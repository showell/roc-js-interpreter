# x86: the JavaScript subset compiled to x86-64, in Roc alone

The code here was written by AI coding agents (Claude), with human supervision.

This folder is the start of an ahead-of-time compiler for the JavaScript subset that `js/` interprets. It will take a program through the interpreter's own front end (`js/roc/`'s Lexer, Parser, Resolve and Compile, to `Bytecode`) and turn the bytecode into a static Linux x86-64 executable. Roc writes every byte of that executable: there is no assembler, linker, LLVM or libc in the product, and the binary needs none to run.

## The milestones

1. **Hello, world.** The instruction encoder, the ELF writer, and the `write` and exit system calls. *Done* (below).
2. **Numbers and functions.** Doubles, calls and returns, `if` and loops; `fib` compiled and timed against node and the VM. *Done* (below).
3. **Heap values with a bump allocator, no collector.** Objects, arrays, strings; as many corpus programs as fit in memory without collecting. *Done* (below): 9 of the corpus's 61 programs, then closures and functions as values, and the array methods that take a function: 14 of 61; then the cheap operators and exceptions: 17 of 61; then console.log's columns, `Math`, `String`, `Object`'s listings, more methods and the spreads: 31 of 61; then the coercions of `+`, index keys, node's quoting, optional chains and node's own errors, Map and Set, and the timers: 45 of 61; then classes: 47 of 61. The corpus's count since is "The corpus", below, held in `x86/corpus.txt`.
4. **The runtime in the subset.** `console.log`'s formatting, Map and Set, number to string, written in the JavaScript subset and compiled by this compiler.
5. **The collector,** and the whole corpus held to node. The collector is *done* (2026-11-27): conservative roots and a non-moving mark-sweep, with headers on every block and a GC-torture tier, as x86/COLLECTOR.md designs it and says of each lane. The corpus is not whole yet ("The corpus", below).
6. **Type specialization,** for long numeric loops. Begun: an integer kind, for loop counters, indexes, parameters, arrays of whole numbers and the bitwise operators ("An integer kind" and "The bitwise operators", below); element kinds in every array's header, and loops versioned on the values they never write (x86/SPECIALIZATION.md, lanes 1 and 2).

**Predicting speed without a stopwatch:** `x86/cost.shale` is a deterministic cost tier. It runs llvm-mca on the bytes this compiler writes, so it reads the same on a busy box as on a quiet one. x86/COST.md explains what it measures and gives its first table. With `counted=1` it also gives each race's exact dynamic instruction count, from js-x86's `counted` mode (`roc/Counter.roc`), by place, by function and in all, with cycles predicted from it.

**Tiny kernels against Roc:** x86/kernels/README.md reads eight small loops, each written in JS and in Roc, instruction by instruction against Roc's release build, and ranks the gaps in our code generation.

**The races' latest verdicts** (the SAT, fib, bank, fourteen, build and collector races, each against node and Roc) are in x86/RACES.md, each with its date, its commit, the box's load and the method.

## What works now (2026-11-25: Map and Set, the timers, and node's errors)

- `roc/X86.roc` encodes the instructions the milestones so far need: `mov` (register, immediate, memory, and `movabs` for an immediate past 32 bits), `lea`, `add`, `sub`, `and`, `or`, `xor`, `cmp` (register or immediate), `imul`, `div` (of a 64-bit register, and of a 32-bit one), `idiv`, `bsr`, `cqo`, `neg`, `test`, `shl`, `shr`, `sar` (by an immediate or by `cl`), `not`, `movsxd`, `mov` of a 32-bit register (which zero-extends), `setcc`, `movzx` of a byte register or of a byte of memory, a byte store, `rep movsb`, `push`, `pop`, `jmp`, `jcc`, `call` (each with a rel32), `call` of a register, `ret`, `syscall`, and the SSE2 doubles `movsd`, `addsd`, `subsd`, `mulsd`, `divsd`, `sqrtsd`, `ucomisd`, `cvtsi2sd`, `cvttsd2si` and `movq`. A memory operand is a base register, an optional scaled index and a displacement, or a displacement from `rip`. Every general register is 64 bits wide but the 32-bit `div`'s divisor; a byte operand is one of `al`, `cl`, `dl` and `bl`, which need no REX prefix. Each instruction's bytes are held to its encoding by an `expect`, 122 of them, including the corner cases of the encoding: `rsp` and `r12` as a base (a SIB byte), `rbp` and `r13` with no displacement (a zero byte of it), and displacements and immediates at the edges of 8 and 32 bits.
- `roc/Assembly.roc` assembles a list of instructions, labels and data into code: a jump, a call or a `lea` that names a label gets a placeholder rel32, patched once every label's place is known, and a `Distance` is 8 bytes holding a label's address less its own, so a record in the read-only segment can name code with no address fixed.
- `roc/Elf.roc` wraps the code as a static executable: an ELF header, one program header and one loadable segment, read and execute, mapped at 0x400000, entry at the code's first byte. The data (the string to print) is read-only, so it shares that segment.
- `roc/Hello.roc` is the driver: given a text, it writes the executable that prints it and exits 0. The hello-world binary is 176 bytes.

- `roc/JsToX86.roc` is the compiler: `js-x86 "<program>"` parses and compiles the program with js/roc's own front end, by import (`js/roc/main.roc` makes `Ast`, `Bytecode`, `Compile` and `Parser` a package), lowers the bytecode (`roc/Lowering.roc`), and writes the executable. `roc/Runtime.roc` is the machine code every executable carries beside its own (about 28 KB of it: `let x = 1;` compiles to a 28,441-byte executable, 2026-11-28): the start, the allocator, buffered output, the stops, and the routines below. `roc/Boxing.roc` holds a value's layout, and `roc/Emit.roc` short builders for the statements the runtime is written in, one instruction a line.

Roc's default platform writes only text to stdout, so each driver prints the executable as hex, and `executables.shale` turns each pair of digits back into its byte. The scripts decide no byte; they only carry them to the file.

**How the encodings were checked:** each `expect`'s bytes were disassembled with binutils' `objdump -D -b binary -mi386:x86-64 -M intel` during development and read back as the instruction the `expect` names, all 119 of them (the bitwise operators' 11, `shl`/`sar`/`shr` by `cl`, `movsxd`, `mov r32, r32` and `not`, on 2026-11-27); the hello-world binary was read with `readelf -h -l` and its code with `objdump`. The product and its checks never run either tool.

## What the compiler compiles

**A value is NaN-boxed, and its kind is known ahead of time where it can be.** Every value's 8 bytes are its boxed bits (`roc/Boxing.roc`):

| top 16 bits | value | low 48 bits |
|---|---|---|
| below 0xFFF9 | a number | (the IEEE double's own) |
| 0xFFF9 | `undefined`, `null`, `false`, `true` | 0, 1, 2, 3 |
| 0xFFFA | a string | its address |
| 0xFFFB | an array | its address |
| 0xFFFC | a plain object | its address |
| 0xFFFD | a function | its closure record's address |
| 0xFFFE | a Map, a Set or an iterator | its record's address |

A number is its double, unchanged; the NaNs x86-64 makes (0x7FF8... for `NaN`, 0xFFF8... for `0 / 0`) lie below every tag, so a value is a number exactly when it is below 0xFFF9 shifted into place, one unsigned compare, and no arithmetic can make a tag. Lowering walks each function's instructions keeping the kind of each slot of the frame and each place on the bytecode's stack: a number, a boolean, `undefined`, `null`, a string, an array, an object, or `Value`, a value whose kind isn't known before it runs; or what takes no bytes (a function by the code it runs, `console`, `console.log`, an array's method looked up). Where two ways meet with two value kinds (a jump's target, a loop's head) the place becomes a `Value`; a loop whose body changes a kind widens its head and lowers the function again. Each loop's head may widen 16 times (Lowering's `most_widenings`), so the walks end; the count is the head's own, so a function of many ordinary loops settles however many it has, and a loop that keeps changing is refused by name (x86/tests/loops-many-heads.js, x86/tests/refused/loop-widenings.js). Since a value's bits are the same whatever is known of it, widening costs no code. A known kind lets the code skip the tag's test: two numbers add with `addsd` and nothing else, as in milestone 2, so fib's code is unchanged but for the stack's check. A `Value` goes through the runtime, which tests the tag (`runtime_add`, `runtime_strict_equal`, `runtime_compare`, `runtime_truthy`, `runtime_check_number` before arithmetic). A function's parameters and its result take their kinds from the whole program: each pass meets every call's argument kinds and every return's kind per function, until both settle.

**Functions and closures.** A function's closure record is 8 bytes holding the distance from them to the code a call through the value enters, 8 holding the distance from them to the text console.log writes (`[Function: f]`, `[Function (anonymous)]`), 8 holding the count of captures, then each capture's cell's address, 8 bytes each. Distances, not addresses, so the same layout serves a record on the heap and one in the read-only segment. A function whose captures are all functions known before the program runs, or numbers held for good such as a top-level `const` set from a number literal (`statics_of` and `constant_numbers` in `KnownFunctions.roc`; fib, which captures only itself, is one), takes no bytes where its kind is known: it is called directly, as in milestone 2, and only where it is used as a value (stored, passed, returned, put in an array or an object, printed) does it become its record in the read-only segment, with no captures. Any other function's `MakeClosure` takes its record from the heap as it runs. A variable a closure captures that holds a value lives in a cell of 8 bytes on the heap, made when its scope starts (the VM's `NewBox`, `FreshBox` and `FilledBox`, and `CopyBox` for a C-form `for`'s next pass), its slot holding the cell's address and its kind `Value`, since writes through other closures are not seen by a walk of one function. A call of a function whose code is known is a direct call, `rbx` holding the record when it has one; the entry copies its captured cells from the record to its slots. Any other call is through the value: stopped unless it is a function, its record in `rbx`, the arguments pushed, their count in `rcx`, and a call of the record's value entry, which takes a missing parameter as `undefined` and leaves an extra argument unread. A function a value may hold takes `Value` parameters (it is `escaping`, worked out with the parameters' kinds until both settle), since no call shows what reaches it that way; one only called directly keeps the kinds its calls give, so fib's code is unchanged. A method call on an object reads the property and calls it through its value, unless it is a class's method (below). A function whose parameters have a pattern, a default or a rest takes its arguments as a call through a value passes them, counted in `rcx`, by either entry, and packs them into an array in its slot (`runtime_pack`), which its own code takes apart.

**Exceptions.** `[r13 + 16]` holds the innermost `try`'s handler, a record of three values on the machine's stack: the handler before it, the frame's `rbp`, and the code a throw enters. `EnterTry` pushes one and `LeaveTry` pops it (every way out of a `try` but a throw passes a `LeaveTry`, the front end's `tries_left`). A throw (`runtime_throw`, the value in `rax`) sets `rsp` to the record, takes the handler before it back, restores `rbp` and returns into the code the record names, which puts the value where the bytecode's stack had its top at the `EnterTry` (a `finally`'s line and column, 0 and 0, under it) and jumps to the handler's instruction. Every frame and runtime routine between is left as it stands, so a throw from a callback of `map` or from a call thousands deep lands the same way. Since a throw may come from anywhere in the `try`, after its variables changed kinds, each variable holds a `Value` at the handler. `new Error(m)`, `TypeError`, `RangeError`, `ReferenceError` and `SyntaxError` make an object holding `name` and `message` and a key no program can name (one byte, 0xFF; a program's strings are ASCII), which marks it an error, so console.log of one stops rather than print what node wouldn't. The stack's overflow throws node's RangeError where a `try` waits.

**The heap and the runtime's registers.** The start maps 3 GiB (`mmap`, `MAP_NORESERVE`, so only what is touched is memory: a heap of 2 GiB, then the collector's mark stack) and sets four registers that no other code writes: `r12` the lowest the stack may reach, `r13` the runtime's state (the output buffer's fill, node's inspect depth, the innermost `try`'s handler, the timers' list, the virtual clock, the counts of timers set and of callbacks run, then 64 KiB of buffer), `r14` the heap's end, `r15` the heap's state. **The heap is 64 KiB pages, each of one block size** (`roc/Heap.roc`, the collector's first lane, x86/COLLECTOR.md): 16, 32, 64 and on to 32768 bytes, and a block past that takes whole pages of its own. Every block starts with a header of 8 bytes, its kind (string, array, items, object, entries, table, closure, cell, collection, collection entries, iterator, timer, or a routine's list of texts) in the top 16 bits, the collector's mark in bit 47 and the bytes asked for in the low 47, and every allocation names its kind (`Heap.allocate(String)`); what it answers is the address past the header, so a value's layout is as before. Allocation pops the class's free list, else bumps through the class's page, taking a free page when the page is full. **A mark-sweep collector frees what is unreachable** (x86/COLLECTOR.md, "Lane 2, as built"): when the bytes taken since the last collection, with those it found live, pass twice those live bytes (and at least 8 MiB, the floor lane 3 measured and kept, x86/COLLECTOR.md, "Lane 3"), it reads the registers, the machine stack and the runtime's places as conservative roots, traces each block by its kind, and sweeps the pages, free blocks onto their class's list and empty pages into runs of free pages. Past the heap's end the program stops with `x86: out of memory: the heap of 2 GiB is full of what is still reachable` on stderr and exit 1. Given the argument `heapwalk`, an executable walks its heap at its exit and at a stop, block by block by header, and stops with `x86: the heap walk found a block whose header is wrong` at the first that isn't; `heapstat` collects once more, walks it and writes its counts after the output (`heap: <n> allocations, <n> collections, <n> pages at most; live at the exit: <n> blocks, <n> bytes asked, <n> bytes in blocks, <n> pages`, the last collection left out of the count). `gcalways`, the torture tier, collects at every allocation and walks the heap after each collection; `gcsample` collects each time 64 KiB more are taken, for a program too big for `gcalways`. `programs.shale` and `fib.shale` run every executable with `heapwalk`, and `programs.shale` runs each again with `gcalways` (`gcsample` for join.js and the SAT race). A string is its length in 8 bytes, then its bytes; a literal sits in the read-only segment in the same layout, each text once, and so do the 256 one-byte strings, which every one-byte string the program makes is (x86/COLLECTOR.md, "Cheaper allocation"). An array is its length, its capacity and its items' address, 8 bytes each; an object is its count, its capacity, its entries' address, its table's address and the count of entries the table covers, its entries 16 bytes each (a key's address and the value), an index key (`"0"`, or digits not starting with 0, below ten digits) placed before the first key that is no index or a greater one, so the entries are in node's order: index keys ascending, then the rest as they were set. A full list is copied to one twice its size. An object of fewer than 8 keys is searched in order; from 8, a key is found by its hash (FNV-1a) in a table of the entries' places, open-addressed and at most half full, made, grown to four times the keys or brought up to date when a key is looked up, and refilled after an index key moves the entries (`roc/ObjectTable.roc`'s header has the rule). The bank race (`bank/`) ran about 5.4 times as many transfers with it. A key the program writes (`o.k`, `o.k = v`, `o.m(...)`) is hashed by the compiler, and the hash handed to the runtime in `r8`, so a lookup in a table hashes no bytes as it runs: about 1.18 times the bank race's transfers again.

**Maps, Sets and iterators** share a tag, 0xFFFE, their record's first word saying which: 0 a Map, 1 a Set, 2 an iterator, 3 a timer. A Map or a Set is its size, the entries used, their room and their address, 16 bytes each (a key and a value, a Set's value its key), in the order first set, then its index's address and the count of entries the index covers; a key is found by SameValueZero, each key made canonical first (-0 made 0, every NaN one NaN), so two keys are the same when their bits are or when both are strings of the same bytes. A Map or a Set of fewer than 8 entries used is searched in order; from 8, a key is found by its hash (a string's bytes' FNV-1a, any other key's bits mixed, so an object by its identity) in an index of the entries' places beside them, open-addressed and at most half full, brought up to date when a key is looked up, as an object's table is (`roc/Collections.roc`'s header has the rules). A string compare takes 8 bytes a step. A deleted entry keeps its place, its key a constant no program makes (`Boxing.gone_bits`), and `clear` deletes each the same way, so a walk under way (`for ... of`, `forEach`, an iterator) meets the entries after its place and those set later, as JavaScript's walks do; nothing is compacted, since the collector moves nothing. In the index a deleted entry's slot stays taken, a tombstone a probe passes, until the index is next made anew. An iterator (`keys`, `values`, `entries` of a Map, a Set or an array) is what it walks, its place and what it gives, so a second loop over it goes on from the first's place. A `for ... of` walks an array, a Map, a Set or an iterator as it is, live, and a string by its characters; a spread or a pattern takes a walk's items. A method of a Map's or a Set's names on a value whose kind isn't known before it runs (`m.get(k)`, `s.add(x)`) goes to `runtime_collection_method`, which calls the receiver's own property of that name when it is no Map or Set, so an object's `add` still works. **`get`, `has`, `delete` and `add` of one argument, and `set` of two, take a guarded fast path first** (BuiltinLowering's `collection_fast_items`): the call site tests the tag (0xFFFE) and the record's first word (a Map's for `get` and `set`, a Set's for `add`, either for `has` and `delete`) in line, then calls the method's routine with the key in `rsi`, with no array of the arguments and no lookup by name; any other receiver or count takes `runtime_collection_method`, which calls the same routines. A `size` on a value is read in line under the same guard.

**A string's methods** (`roc/StringMethods.roc`) have one routine each, which takes the string in `rdi`, its first two arguments in `rsi` and `rdx` (`undefined` for one not given) and their count in `rcx`. On a string known before the program runs the call is the routine's; on a `Value` (`line.trim()`, `line` an item of `split`'s array) it is `runtime_string_method`'s, which calls the same routine when the value is a string and the value's own property of the method's name otherwise, as `runtime_collection_method` does, so an object's or a class's `trim` still works, and an array or a number stops as any property it lacks. The methods a string shares with an array (`indexOf`, `includes`, `slice`, `lastIndexOf`) have routines that take either receiver.

**Timers** run after the program on a virtual clock, as js/README.md describes: the program's code ends by jumping to `runtime_run_timers`, which runs the earliest timer due that is neither cleared nor done, two due at once in the order set, the clock moved to its time. A delay that isn't between 1 and 2^31 - 1 (left out, 0, negative, NaN) is 1, as node makes it, and any other its whole part; an interval is set again from its time after its callback, unless the callback cleared it, so a timer its callback sets for the same time runs first, as in node. After 100,000 callbacks the program stops with a line saying so (an interval never cleared runs for good in node). A throw nothing catches in a callback stops the program with exit 1, as a throw in the program's own code does.

**Output is buffered.** console.log writes into the buffer, which is written when the next bytes wouldn't fit, before a stop's message, and at the exit; a write the kernel cuts short is written on until every byte is. `many-lines.js` prints 20,000 lines through it.

**Stack overflow.** Every function's entry checks its frame against `r12`, 6 MiB below the start's stack (Linux gives 8 MiB; the rest is the runtime's). Past it the program writes `RangeError: Maximum call stack size exceeded` to stderr and exits 1, as node does for an uncaught RangeError, whose stderr has that same line after the source line and a caret, and a stack trace after. How deep differs: node throws between 9,000 and 10,000 calls of `function d(n) { return n === 0 ? 0 : 1 + d(n - 1); }`, the executable between 80,000 and 90,000 (its frames are about 72 bytes), so a recursion between the two runs here and throws in node. A `try` that waits catches it as node's RangeError.

**A frame is fixed per function**: below `rbp`, its slots, then the bytecode's stack as deep as the function ever makes it, so every push and pop is a load or a store at a known place. A call pushes its arguments, the last first, and the callee copies them to its parameters' slots; the result comes back in `rax`.

## An integer kind (the design, 2026-11-26)

Today every number is a double. A number proved whole is turned into an integer at every array index, every `%` and every `Math.floor` (`cvttsd2si`), and back into a double after (`cvtsi2sd`). The fib race's loop counter and the fourteen race's `Math.floor(program / place) % 4` pay for that. This is the design of a kind whose bits are an integer; x86/race/README.md (fix 17) and x86/fourteen/README.md ("What is left") say what led to it.

**The kind.** `Integer({ low, high })`: a slot or a stack place whose 8 bytes are a two's-complement integer, known to lie between `low` and `high`, both within ±2^53. Every whole number in that range is exactly a double, so an `Integer` is a double that happens to be kept as an integer: converting it is exact, and no value it can hold is one JavaScript would have rounded. An `Integer` is never -0, NaN or an infinity. The bounds are what make the integer arithmetic safe without a check: an operation whose bounds would leave ±2^53 gives a `Number`, not an `Integer`. The order is `Integer ⊑ Number ⊑ Value`: two `Integer`s meet as the `Integer` of both ranges, an `Integer` and a `Number` as a `Number`, and the `Integer`'s side converts.

**Why bounds and not a check.** A kind is fixed when the function is lowered, so a check that finds an overflow as the program runs has no kind to fall back to: a value past 2^53, or -0, can't be held in an `Integer`, and stopping the program there would be a difference from node. So an `Integer` only comes from what is proved in range, and everything else stays a double, as today.

**Where an `Integer` comes from:**
- a whole number literal of at most 2^53 that an instruction able to take an `Integer` uses next (a store to a slot, `+ - *`, `%`, an index), as `Integer({ low: n, high: n })`; anywhere else a literal is a double, as today, so `console.log(3)` costs nothing new;
- `+`, `-` and `*` of two `Integer`s, when the result's bounds stay within ±2^53 (`0 * -1` is -0 in JavaScript: a product's bounds that may give a zero from a negative factor give a `Number`);
- `%` of two `Integer`s whose dividend is at least 0 (a negative dividend can give -0) and whose divisor's range holds no 0 (`x % 0` is NaN); its bounds are 0 to one less than the divisor's largest size, at most the dividend's most;
- `Math.floor` of `/` of two `Integer`s, the divisor at least 1 (no NaN, infinity or -0 is possible), the dividend of either sign, rounded down; and `Math.floor`, `ceil`, `round` and `trunc` of an `Integer`, which are it;
- an array's or a string's `.length`, between 0 and 2^32;
- a loop's counter: a slot that is an `Integer` where the loop is entered and an `Integer` on every way back.

`Math.floor` of a division by a `Number` stays a double: the divisor may be 0 or negative, so the floor may be an infinity or -0. The fourteen race's `program / place` is one of two `Integer`s since step 4: `place` is an item of an array of whole numbers, and `program` comes of a parameter that every call passes an `Integer`.

**Where an `Integer` becomes a double.** Before any instruction that doesn't take an `Integer`, each `Integer` on the stack is converted in place (`cvtsi2sd`, then the double stored back): a call's arguments (but a direct call's, where the parameter is an `Integer`: step 4, below), a return (so a result is never an `Integer`), console.log, a store into an array or an object, a meeting with a `Value`, arithmetic with a `Number`, an ordering or an equality with a double, and every instruction not named among the `Integer`'s consumers below. The rule is one place in the walk (`values_made`, beside the one that makes a function known by its code a value), so a consumer that takes an `Integer` says so, and any other is safe by default.

**What takes an `Integer` directly:** a store or a set of a slot; a load of a slot; `Pop`; `+ - * %` and `Math.floor(a / b)` of two `Integer`s (above); an ordering or an equality of two `Integer`s (`cmp`, and its jumps); an array's item read or write at an `Integer` index, whose range test is one unsigned `cmp` against the length, with no `cvttsd2si`.

**Where two ways meet.** The stack never carries an `Integer` across a meeting: before a jump, and on the way that falls to a place a jump also reaches, each `Integer` on the stack is converted. A slot may: two `Integer`s meet as the `Integer` of both ranges. A slot that meets an `Integer` on one way and anything else on another is demoted: the function is lowered again with that slot never an `Integer` (a store of an `Integer` to it converts first), as a loop's head is widened today.

**A loop's head.** The head takes the kinds that fall to it, and each way back is met with them. An `Integer` slot whose range grows on the way back (`i = i + 1`) is widened on the side it grew, to ±2^53 there, each side at most once, so the walks still end and a counter that only climbs keeps its least. An ordering of an `Integer` slot with an `Integer` that jumps out of the loop narrows the slot's range on the way that stays (`i < n`, with `n` a length, gives `i` at most 2^32 - 1 inside the loop), so `i + 1` stays an `Integer`. A slot that comes back a `Number` is demoted.

**Registers.** An `Integer` is 8 bytes in the frame or the stack as any value is, so Registers' renaming of the frame's places to `r9`, `r10`, `r11` and `rbx` takes `Integer` places with no change: a counter in a spare register is then `add r9, 1`, and an index used as it is.

**Out of scope:** an `Integer` result (a return converts); an `Integer` in a cell (a captured variable is a `Value`); deoptimization, lowering a function twice and moving between the two as it runs.

**Where it stands (2026-11-26).** Step 2 is in, narrowed to what a loop counter needs. A whole literal is an `Integer` where the next instruction takes one (Lowering's `integer_literal`: a store or set of a slot that isn't demoted and holds no cell, `+ - *` with an `Integer` below that stays one, an ordering with an `Integer` below that its `JumpIfFalse` follows, an index); `+ - *` of two `Integer`s are integer arithmetic within their bounds (`LoweringBasics.integer_arithmetic`, a product that may be -0 none), and so are `++` and `--` of an `Integer` slot; an ordering of two `Integer`s and its `JumpIfFalse` are a `cmp` and a signed jump that narrow the slot each side came from on the way that stays (`OperatorLowering.integer_jump_items`); a known array's or string's `.length` is an `Integer` of 0 to 2^32; and an item read or write at an `Integer` index loads it as it is, with one unsigned `cmp` and no `cvttsd2si` (its slow way makes it a double first). The stack's `Integer`s are made doubles place by place (`integers_kept`), so a counter below an operand stays one, and a conversion no longer forgets what the straight run proved of index checks. A head whose `Integer`s alone widen, as a demotion, counts against no limit of walks. A program with a `try` makes no `Integer` literal (a throw lands with every variable a value). Moves joins a move into an operation's source and a compare's first, and steps a register in place (`mov rax, r9`, `add rax, 1`, `mov r9, rax` is `add r9, 1`). In the fib race's `addInto`, `i` and `aLength` are integers: its first loop went from 71 instructions a limb to 64 with no conversion left in it, and F(100000) from about 1,000 ms to about 880 ms (medians of 5 and 7, alternated, load 0.6 to 3.5); the bank and fourteen races are as they were (bank's transfer loop is the same code). A counter tested against a parameter (`steps`' `j < k`, `k` a double) can't be narrowed, so it is demoted and stays a double, as designed; it is an outer loop. Seven expects hold the rules (the bounds at ±2^53, the -0 products, the literals, the narrowing, and a counter with no conversion against one demoted), and x86/tests/integer-counters.js holds counters and their near misses to node. 
Step 3 is in: `%`, `Math.floor(a / b)` and `===` of `Integer`s. `%` of two `Integer`s is integer arithmetic (`LoweringBasics.integer_remainder`, above), lowered by `OperatorLowering.integer_remainder_items`: a divisor whose range is one value is a constant (a power of two an `and`, any other the magic multiply that `%` of numbers uses), any other an `idiv`. A `/` of two `Integer`s that a call of `Math.floor` takes at once is lowered with the call as one (Lowering's `integer_binary` and `fused_jump`, `OperatorLowering.integer_floor_items`): a power of two a `sar`, any other constant the magic multiply, any other divisor an `idiv`, each with the remainder's sign taken in where the dividend may be negative. `===` and `!==` of two `Integer`s fuse with their `JumpIfFalse` as an ordering does, a `cmp` and a jump, and `===` narrows both sides on the way it holds. A loop's head widens an `Integer` only on the side it grew, so a counter from 0 stays at least 0 and `i % 4` in its loop qualifies. x86/tests/integer-division.js's hot loop (`Math.floor(i / 16) % 4`, `i % width`, `Math.floor(i / width)`, three equalities) went from 215 instructions and 6 calls in its body to 94 and none. The fourteen race's `Math.floor(program / place) % 4` is unchanged: `place` is an item of an array of numbers, a double, and `program` a parameter. Next: Integer parameters, so `steps`' `k` narrows `j`, and arrays of integers; then a look at what Registers does with them (the index still goes through three register copies, which the range test's jump to a stop keeps: x86/race/README.md, "What is left", 3).
Step 4 is in: `Integer` parameters and arrays of whole numbers. A parameter of a function known by its code, which no value may hold, is an `Integer` when every direct call passes one, its range the hull of theirs (Lowering's `integer_arguments`; `call_kinds` takes each argument's kind before it is made a double, so the passes' first guess of a number rises to it). A literal argument is an `Integer` (`integer_argument`); a call that passes a double makes the parameter a number (`met_kind` meets an `Integer` with a number as a number); a range that grew since the last pass is widened on that side to ±2^53, so `f(n - 1)` settles (`parameters_widened`); and a parameter a closure captures, or that the walk demotes, is made a double at the entry (`entry_doubles`). An array literal of whole number literals is `Integers({ low, high })`, its items doubles as an array of numbers' are, so the runtime and printing are unchanged, and each item read or walked is an `Integer` by one `cvttsd2si` (Lowering's header, `INTEGER ARRAYS`). A write or push of anything but an `Integer` within its range, a parameter given two ranges, or any other refusal lowers the program again with arrays of doubles, then with none. x86/tests/integer-parameters.js, integer-arrays.js and integer-arrays-missed.js hold them to node, and six expects the rules. The fourteen race's `f` loop body went from 86 instructions and 3 calls (`Math.floor`'s routine, `%`'s slow way, `step`) to 46 and 1 (`step`), read statically with objdump: `Math.floor(program / place)` is an `idiv` and `% 4` an `and`, and `step`'s `op` is an `Integer` whose `===`s are `cmp`s. Out of reach still: two literals of different ranges passed to one parameter (they fall back to doubles), `push` of a literal, and results.
The 32-bit divide is in (x86/fourteen/STEP_STUDY.md, recommendation 1): a floor or a remainder whose divisor isn't a constant, with a dividend in [0, 2^32) and a divisor in [1, 2^32) (`OperatorLowering.fits_div32`), is `xor rdx, rdx; div ecx` (`X86.Div32`) instead of `cqo; idiv rcx`. Unsigned, its quotient is the floor and its remainder is 0 or more, as the dividend is. The operands stay 64-bit loads, since a value in that range has a zero high half, and the `div` writes `eax` and `edx`, which zero-extends both. On this CPU (Skylake-SP or Cascade Lake) a `div r32` takes about 4 ns and an `idiv r64` about 10. ## The bitwise operators (2026-11-27)

`&`, `|`, `^`, `<<`, `>>`, `>>>` and `~`, and their compound assignments, are ECMAScript's: each operand made a 32-bit integer (ToInt32, ToUint32 for `>>>`'s first), a shift's count taken modulo 32, the answer a signed 32-bit integer (unsigned for `>>>`). The front end parses them as js/README.md says and the interpreter's rule (`ValueRules.word_of`) is the compiler's too, for an operand known before the program runs.

**Each operand is made its 32-bit integer in its own place** (`OperatorLowering.word_items`), as 64 bits whose low 32 are its ToInt32: an `Integer`'s bits are that already (every integer within ±2^53 wraps to its low 32 bits as two's complement does), a constant (an `Integer` of one value, or a number literal) is an immediate, a number is `cvttsd2si`'s in line, and a `Value` is `runtime_word_of`'s, which stops the program unless it is a number (`x86: arithmetic on a value that is not a number is not compiled yet`, as for `-`). `cvttsd2si` gives -2^63 for NaN, an infinity and a number of 2^63 or more in size, the one value `cmp rax, 1` overflows on, so `jno` passes every other and the routine takes those: NaN and the infinities are 0, and a number past 2^63 is its mantissa shifted by its exponent (0 past 2^84). Another kind (a string, a boolean, `undefined`, `null`) is refused when its kind is known before the program runs, as the interpreter refuses the coercion: ``refused: `|` of a string and a number is not compiled yet``.

**The operator is one instruction on `rax`'s low 32 bits** (`and`, `or`, `xor`, `shl`, `sar`, `shr`, `not`; a second operand an immediate when it is known, else `rcx`), then `movsxd rax, eax` makes the answer the signed 32-bit integer it is. `>>` sign-extends its first operand before it shifts and `>>>` zero-extends it (`mov eax, eax`); a count known only as the program runs is made modulo 32 (`and rcx, 31`) before `shl rax, cl`, since the 64-bit shifts take it modulo 64. `&` with a side that lies in 0 to 2^31 - 1 needs no `movsxd`.

**The answer is an `Integer`, whatever the operands' kinds**, its range from `LoweringBasics.bitwise_kind` (seven expects hold it): any 32-bit integer, narrowed where an operand's range lies within 32 bits: `x & m` is 0 to `m` when `m` can't be negative; `|` and `^` of two that can't be negative are 0 to the larger one's bits filled (`ones_through`); `x << k`, `x >> k` and `x >>> k` of a known count shift the range's ends (`<<` only while both stay within 32 bits); `>>` by any count keeps the range with 0 or -1 taken in, `>>>` by any count is 0 to its most, and `>>> k` of anything is 0 to 2^32 - 1 shifted; `~` mirrors its range less 1. So `i & 7` indexes an array as an integer and `(x >>> 0) % 4` is an `idiv` of integers. A program with a `try` makes no `Integer`, so there the answer is made a double. Both operands of a bitwise operator are kept as the `Integer`s they are (Lowering's `integers_kept`), a literal beside one is an `Integer` (`integer_binary`), and IndexLowering takes the answer as whole.

x86/tests/bitwise-integers.js (counters, ranges into an index and `%`, a string hash, unsigned words whose product passes 2^53, counts from -2 to 61, `~~`, a bitset), bitwise-values.js (seven operators of 26 edge values through a function a value may hold, and doubles in line), bitwise-try.js and the corpus's 62-bitwise.js and 63-bitwise-kernel.js hold it to node; three programs in tests/refused/ hold the refusals and the stop. A program with no bitwise operator carries no `runtime_word_of` (Jumps drops a routine nothing names), so x86/fib.js and the fib, bank and fourteen races compile to the same bytes as on master e876665; their executables, timed alternately with master's (medians of 5 CPU times, niced, load 2.4 to 3.8): fib 14 and 14 ms, F(100000) 838 and 864 ms, 2,000,000 transfers 393 and 377 ms, fourteen at 300 rounds 425 and 428 ms, the same bytes either way.

## Inlining small leaves (2026-11-26)

`roc/Inlining.roc` puts a small leaf function in line at a direct call inside a loop, in the bytecode, before anything is lowered: the call's load of the function goes, each argument is set into a slot of its own appended to the caller's frame, and each `return` is a jump to the instruction after the call, so the lowering walks the body with that site's exact argument kinds. Its header has the budget (a leaf of at most `most_leaf_instructions`, 64, reachable instructions, called inside a loop; each caller grown by at most the larger of `most_growth_percent`, 25, of its own instructions and `least_growth_instructions`, 64, and never past `most_growth_instructions`, 256; a leaf of at most `always_leaf_instructions`, 16, inlined past the caller's share though never past the 256) and what it leaves alone (a program with a `try`, a callee with captures other than constant numbers, a call whose arguments aren't a straight run). The lowering takes the inlined program first and the program as it was when that is refused, so inlining never refuses a program. `js-x86 "<program>" inlined` prints how many sites and instructions it inlined, and `programs.shale` holds the total across `tests/` (47 sites, 683 instructions) and the count a test's first line names. x86/tests/inline-*.js hold the sites and their near misses to node, and each rule of the budget was planted once (a size limit of 400, a growth of 2500%, no `try` rule, no loop rule, a call taken as a leaf's; then, with today's numbers, a size limit of 400, a share of 0%, a floor of 0, no cap and no small-leaf rule) and turned a count red: inline-too-big.js holds the size limit, the leaf rule and the floor, inline-share.js the percentage, and inline-small.js the small-leaf rule and the cap.

**The numbers (2026-11-26) follow V8's** (x86/fourteen/STEP_STUDY.md, sections 3 and 4): its limits are absolute per function (a 460-byte callee, 920 bytes inlined in all, 27 bytes always inlined), and one of our instructions is about 1.7 of its bytecode bytes, so ours are about a quarter of its callee limit, half of its cumulative one and its small-function one. The floor is what lets a small caller take one leaf: a percentage alone shut out fourteen's `f` (40 instructions) taking `step` (44). Now `step` is inlined there (1 site, 45 instructions; the executable at 300 rounds 24,106 to 24,498 bytes), and at 300 rounds, 7 CPU times of each alternated against master 16759b7, niced, load 0.80 to 0.82: **median 541 ms before, 472 ms after (13% less).** The bank race (1 site) and the fib races (none) compile to the same bytes as before. `run` stays a double in the inlined body (recommendation 3 of the study).

Before those numbers (40 instructions, 25%), `step` was not inlined. With the limits at 48 instructions and 150%, `f`'s loop is 118 instructions in all and no call of `step` (46 and one call before); `op` is an `Integer` in the inlined body (`cmp r10, 1`), but `run` stays a double, since the body's returns meet as numbers. At 300 rounds, alternated, medians of 9 CPU times at a load of about 3.5: 758 ms against 645 ms. The bank race inlines one site (no change in its time); the fib race none.

## Running it

From the repository's root:

    shale x86/hello.shale            # the encoder's expects, then the hello-world executable
    shale x86/programs.shale         # each program in x86/tests/ held to node, each in tests/refused/ to its refusal, the corpus to x86/corpus.txt
    shale x86/programs.shale corpus=report   # the same, with each corpus program's reason, grouped
    shale x86/fib.shale              # the compiler's expects, fib held to node, then the times
    shale x86/fib.shale timing=0     # the same without the times

`hello.shale` runs the backend's expects (`roc test x86/roc/Hello.roc`, which runs every imported module's), their number held to its `EXPECTS`, builds the driver on the dev backend, writes the executable under the build mount, runs it, and holds its output (`Hello, world!` and a newline) and its exit code (0) exactly. `programs.shale` compiles each program in `tests/` and holds what its executable prints and its exit code to node's, exactly; each program in `tests/refused/` names in its first line the refusal js-x86 must print (`// refused: <text>`) or the line its executable must stop with (`// stops: <text>`); then the corpus, as above. `fib.shale` runs the compiler's expects, their number held to its `EXPECTS` (the encoder's, LoweringBasics' of the integer kind's ranges and the bitwise operators', Boxing's, StringMethods', Forwarding's, KnownFunctions' constant numbers, Lowering's of arrays of numbers, IndexLowering's of index checks proved once, RuntimePosts' that the runtime's post-passes done once hold, and the ones of js/roc that the front end brings), then fib to node, then times the executable, node and js-vm's release build; it never starts a release build, and says so when the cache holds none of today's inputs (`tools/roc_build.shale cached=1`). `shale check.shale` runs all three (fib with `timing=0`), and runs `roc fmt --check` and `roc check` over this folder as over the rest.

The drivers alone, once built: `x86-hello "Hello, world!"` and `js-x86 "<program>"` print an executable's bytes as hex; a program js-x86 refuses ends with a line `js-x86: <why>` and exit 1.

`x86/lints.shale` and `x86/accepted_terms.txt` give Shale's Roc lints the manuals' short words (`rax`, `lea`, `rex`), which they would otherwise read as abbreviations.
